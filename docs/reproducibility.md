# Reproducibility and Evidence Guide

This document defines how the lab should be run and how measured artifacts should be interpreted.

## 1. Reproducibility

The project targets a Linux/Ubuntu environment with the required OpenLane/OpenROAD tools and SKY130 PDK installed locally.

The repository stores:
- RTL and flow configuration
- Timing constraints
- Experiment scripts
- Curated result tables
- Selected signoff reports

Large generated run directories and complete tool/PDK installations remain local and are intentionally excluded from Git.

## 2. Configuration discipline

Two configuration layers are retained:

- `configs/config.json` contains the reusable baseline flow settings.
- `designs/riscv32/config.json` is the design-specific configuration used by the OpenLane-style experiment scripts.

Several sweep scripts intentionally rewrite `designs/riscv32/config.json` for each run. Do not execute those scripts concurrently against the same working directory.

For a new experiment:
1. Start from a known baseline.
2. Change only the parameters being studied.
3. Give the run a unique tag.
4. Preserve the generated result summary in `results/`.
5. Record whether the run completed successfully before interpreting the numbers.

## 3. Evidence policy

A result is considered **captured** only when the repository contains the corresponding numeric output or report generated by a real run.

A file containing only a CSV header is **not** treated as an experiment result. Such artifacts are kept as placeholders when they document the intended measurement schema.

The status manifest in `results/experiment_status.csv` distinguishes captured data from placeholder outputs.

## 4. Timing and signoff interpretation

Use the saved reports as evidence rather than assuming a successful flow implies timing closure.

For timing analysis, inspect:
- setup WNS/TNS
- hold WHS/THS
- worst-path reports
- clock uncertainty and latency
- post-route parasitic timing where available

For physical verification, inspect:
- routing/DRC violations
- LVS errors
- XOR differences
- antenna reports

The repository includes both passing and failed/negative test evidence. Failed experiments are retained when they are useful for explaining how timing or physical constraints affect the flow.

## 5. Suggested experiment record

For every new study, keep the following information:

```text
Experiment name
Run tag
Design / RTL revision
Clock period
Floorplan utilization
Placement target density
CTS settings
Routing settings
Tool / PDK environment
Flow status
WNS / TNS
WHS / THS
Area
Routing / DRC status
LVS / XOR status
Notes on the observed trade-off
```

This keeps the repository closer to an engineering lab notebook than a collection of disconnected screenshots.
